# Demo Mode Parity — Design Spec

## Context

Away-from-home demo mode (`2026-09-09-away-from-home-demo-mode-design.md`,
PR #22) lets the phone hold a full story conversation with Elsie using
Groq's hosted LLM and speech-to-text plus the phone's own TTS when the home
Mac is unreachable. It works by giving `SessionCoordinator` a second
`ServerConnecting` conformer, `DemoConnection`, that speaks the same
`ClientMessage`/`ServerEvent` vocabulary as the real server.

Since that spec was written, `main` has gained features built entirely on
wire messages that only the real server implements: story-length settings
(`update_settings`, PR #20), storybook persistence and The End's
auto-navigation (`conclude_story`, `rewriting_started`/`rewriting_done`,
`list_stories`/`get_story`, PRs #13/#17), storybook page art
(`get_page_image`, PR #27), and the real Library/Reading screens
(`synthesize_page`, PR #42). `DemoConnection.send(_:)` handles all of them
with one grouped no-op case, so away from home:

- the story-length settings have no effect;
- "Finish this story" does nothing;
- The End never appears (`SessionCoordinator.readyToShowTheEnd` needs a
  `rewriting_started` event that `DemoConnection` never emits);
- Library shows nothing (or, by code reading, stale cards left over from a
  server session in the same app process, whose Reading screen then stays
  blank forever because `get_story` is never answered);
- 🔊 never narrates: the request is silently ignored, so the page-audio
  waiting ditty would simply loop until its 45 s timeout;
- pages have no illustrations.

These are tracked as #24 (the general class of gap) and #26/#33
(illustrations), and closing them is the household's stated top priority as
of 2026-09-19. The original demo-mode spec deferred browsing demo-made
stories on the grounds that Library/Reading were still mock-data-only
("solving a problem that doesn't exist"); PR #42 removed that rationale.

One further fact shapes the sync design. Today a synced story's server-side
rewrite (`SessionRunner._run_synced_rewrite`, `server/tinytalk/session.py`)
calls `storybook.build_and_attach` **without an image backend** — only the
live-story `_run_rewrite` passes one. Stories synced from demo mode
therefore get text-only pages at home. Illustrations created away from
home cannot be regenerated by the Mac afterwards; they must travel with the
story.

## Goals

1. Away from home, the full story-to-storybook loop works with the existing
   screens: story-length settings apply, "Finish this story" works, The End
   appears automatically, Library lists the story, Reading shows its pages,
   🔊 reads a page aloud, and each page has an illustration (when
   Cloudflare credentials are set; see goal 3).
2. A story's finished storybook (title, pages, epilogue, illustrations)
   reaches the home library intact when the phone reconnects to the Mac —
   nothing generated away from home is discarded or redone.
3. Free to run, with nothing new mandatory: Phase 1 needs only the Groq key
   demo mode already requires; illustrations need optional Cloudflare
   credentials, and without them storybooks are simply text-only.
4. This class of silent gap cannot recur unnoticed: a test forces an
   explicit demo-mode decision for every `ClientMessage` case.

## Non-goals

- Keeping stories on the phone after they sync. They then live on the Mac;
  Library while away shows the stories made since the last sync.
- Caching the Mac's library on the phone for offline browsing.
- On-device image generation (Core ML Stable Diffusion). See Decisions.
- Per-story page counts.
- FLUX.2 reference-image consistency, unless on-device testing shows the
  simpler approach isn't good enough (see Risks).
- Fixing #39 (mic silently dead after a demo→server switch). It is a
  separate bug track, but this work must not make it worse.
- Fixing #41 for demo mode (Landing's "Read Stories" greyed out on cold
  launch). A possible tiny follow-up.
- Android.
- Any change to the server's live-conversation or live-rewrite path. The
  only server change is the sync endpoint's validator (see Sync).

## Decisions and alternatives considered

Made with the household on 2026-09-19.

| Question | Decision | Rejected, and why |
|---|---|---|
| How much of the experience works away from home? | The full loop **including illustrations**. | *Text pages only, art later* — the Mac never generates art for synced stories, so "later" doesn't exist. *Just stop the silent no-ops* — a demo couldn't show the storybook. |
| Architecture | **`DemoConnection` acts as a local server**: it answers the same wire messages and emits the same events, so Library/Reading/The End are unchanged. | *A data-source abstraction in `AppModel`* — cleaner in principle, but it rewires the on-device-verified poll loop, pending-fetch state and page-audio plumbing (higher regression risk, larger diff). |
| Image source | **Cloudflare Workers AI, FLUX.1 [schnell]**, behind a swappable interface. | *Pollinations* — free and keyless but no uptime guarantee, limits change without notice. *On-device Core ML Stable Diffusion* — ~1 GB model, roughly 10–35 s per image on iPhone 13-class chips, memory-crash reports on 6 GB devices, no LoRA/IP-Adapter consistency path. *Gemini image models* — no free tier for image output. *Hugging Face* — free credit is trivial. |
| What happens to a demo story's storybook at sync? | **Upload the finished storybook** with the transcript; the Mac validates and stores it as-is. | *Regenerate at home* — discards the away art and would run image generation outside the REWRITING gate (Ollama/Stable Diffusion memory contention). *Transcript only, as today* — art would vanish on sync. |
| Should demo mode gate new stories while a rewrite runs? | **No.** | The server's REWRITING gate exists because one local Ollama/Stable Diffusion process shares one memory budget. Cloud backends have no such budget. (Builds are still serialized so rewrites never overlap.) This also means #32's silent hang cannot occur in demo mode. |
| What does Library show away from home? | Stories made since the last sync. | Keeping synced copies or mirroring the Mac's library — YAGNI for a demo path. |

### Research (verified 2026-09-19 against primary sources; re-check before relying)

- **Cloudflare Workers AI** free allocation is 10,000 neurons/day, no charge;
  when exhausted, requests fail until the daily reset unless the account
  is upgraded to the paid plan. The docs list FLUX.1 [schnell] at 4.80
  neurons per 512×512 tile; a secondary calculation that adds a per-step
  charge puts a default 1024×1024, 4-step image at roughly 58 neurons —
  about 170 images/day, or about 34 five-page stories (re-check the exact
  figure at implementation). The docs do not state whether the free tier requires a payment
  card (they say only that "some models require a paid billing method").
  The catalog also has FLUX.2 [dev]/[klein] models with multi-reference or
  editing support, a possible route to character consistency later.
  Request: `POST /client/v4/accounts/{account_id}/ai/run/@cf/black-forest-labs/flux-1-schnell`,
  `Authorization: Bearer {token}`, JSON `prompt` (required, ≤ 2048 chars),
  `steps` (default 4, max 8), optional `seed`; no width/height parameter is
  documented. The image comes back as a base64 JPEG.
- **Gemini API:** Google's pricing page lists "Free Tier: Not available" for
  every image-output model, and Gemini 2.5 Flash Image is deprecated and
  shuts down 2026-10-02.
- **On-device Stable Diffusion:** Apple's `ml-stable-diffusion` benchmarks
  put iPhone 13-class devices at roughly 10–35 s per 512×512 image with
  palettized (~1 GB) models; there are reports of memory crashes on 6 GB
  devices even with the increased-memory-limit capability.

Sources: developers.cloudflare.com/workers-ai/platform/pricing/,
developers.cloudflare.com/workers-ai/models/,
developers.cloudflare.com/workers-ai/models/flux-1-schnell/,
ai.google.dev/gemini-api/docs/pricing, github.com/apple/ml-stable-diffusion.

## Architecture

`SessionCoordinator`, `AppModel`, `LibraryView`, `ReadingView` and
`TheEndView` are driven entirely by wire events. If `DemoConnection`
produces the events a real server would, none of them need to change. The
new work is therefore a second implementation of the server's *story
browsing* half, living next to the *conversation* half `DemoConnection`
already implements.

```
SessionCoordinator ──ClientMessage──▶ DemoConnection ──▶ DemoStoryLibrary ──▶ LocalStoryStore
       ▲                                   │                    │
       └────────────ServerEvent────────────┘                    ├──▶ StorybookWriter ──▶ ChatCompleting (Groq)
                                                                └──▶ IllustrationPass ──▶ ChatCompleting + ImageGenerating (Cloudflare)
```

Everything below lives in `TinyTalkCore` (pure Swift, testable with fakes
under the project's existing "protocol seams tested with fakes"
convention). `AppModel`/Settings changes are small and listed separately.

### Components

| Unit | Purpose | Depends on |
|---|---|---|
| `DemoConnection` (extended) | Speaks the server's half of the wire protocol for story browsing: answers `list_stories`, `get_story`, `synthesize_page`, `get_page_image`, `update_settings`, `conclude_story`, and emits `rewriting_started`/`rewriting_done`. `send(_:)` becomes exhaustive with no grouped no-op. | `DemoStoryLibrary`, existing Groq/TTS clients |
| `DemoStoryLibrary` (new) | The local library: save a finished story, list, detail, page text, page image. Runs one storybook build at a time. Produces sync payloads. | `LocalStoryStore`, `StorybookWriter`, `IllustrationPass?` |
| `LocalStoryStore` (new) | File-backed store in Application Support: `<id>.json` plus `<id>/page-<i>.jpg`. Lock-guarded, like `PendingDemoStore`. | Foundation |
| `StorybookWriter` (new) | Swift port of `server/tinytalk/storybook.py`. | `ChatCompleting`, `Safety.findBlocked` |
| `Safety.findBlocked` (new) | Port of `safety.find_blocked`: returns the blocked terms in a text. Needed by the storybook safety retry. | — |
| `IllustrationPass` (new, Phase 2) | Port of `server/tinytalk/illustrations.py`. | `ChatCompleting`, `ImageGenerating` |
| `ImageGenerating` + `CloudflareImageClient` (new, Phase 2) | Swappable image backend and its Cloudflare implementation. | a URLSession seam |

`PendingDemoStore` is **unchanged** and remains the sync queue of
transcript payloads. A story's local storybook is an enrichment keyed by the
same id, so stories completed before this change (which have no local
storybook) still sync the old way.

Signatures below are illustrative shapes, not final.

**`StorybookWriter`** — a faithful port of `storybook.py`: the same system
prompt, rewrite prompt (with the page count from the story's settings and
the optional epilogue key), parse-retry and safety-retry templates, the
same tolerant JSON extraction (first `{` to last `}`), and the same 3
attempts (`config.STORYBOOK_REWRITE_RETRY_ATTEMPTS`) shared between the two
retry causes. As on the server, the model's own epilogue text is never
used: when the story shared real animal facts the epilogue is always
`"And one true thing we learned about the {animal}: {fact}"` from the first
shared fact, otherwise there is none. Returns `nil` for "failed" (unparseable
or unsafe after every attempt, or the chat call threw).

```swift
struct WrittenStorybook { let title: String; let pages: [String]; let epilogue: String? }
func write(turns: [PendingDemoStoryTurn], sharedFacts: [[String]], pageCount: Int) async -> WrittenStorybook?
```

**`LocalStory`** (the store's record, `Codable`): `id`, `createdAt` (ISO 8601),
`turns`, `sharedFacts`, `pageCount` (the target the story was created with),
`title?`, `pages` (`[{text, hasImage}]`), `epilogue?`, `rewriteStatus`
(`pending`/`done`/`failed`), `illustrationsStatus?`
(`pending`/`done`/`partial`/`failed`). These mirror `story_store.py`'s
fields and the existing `SavedStorySummary`/`SavedStoryDetail` types, so the
mapping to what the UI consumes is direct.

**`DemoStoryLibrary`**:

```swift
func begin(_ payload: PendingDemoStoryPayload, pageCount: Int)   // saves transcript, status pending
func list() -> [SavedStorySummary]                                // newest first
func detail(id: String) -> SavedStoryDetail?
func pageText(id: String, index: Int) -> String?
func pageImage(id: String, index: Int) -> Data?
func buildStorybook(id: String) async                             // serialized; rewrite, then art

// Needs only the store, not a live library, because the sync runs from the
// server-connect path, where no DemoStoryLibrary exists:
static func syncPayloads(store: LocalStoryStore, pending: [PendingDemoStoryPayload]) -> [DemoSyncStory]
```

`DemoSyncStory` is the existing `PendingDemoStoryPayload` plus an optional
finished storybook (title, pages with optional JPEG bytes, illustrations
status). Removing synced stories is `LocalStoryStore.remove(ids:)`.

**`ImageGenerating`** and **`IllustrationPass`** (Phase 2). The pass mirrors
`illustrations.py`: first ask the LLM (Groq) for a one-sentence, ≤ 25-word
scene description per page (same template), then generate strictly in page
order — page 0 without a reference, later pages passing page 0's image as
the reference *when the backend supports it* (FLUX.1 [schnell] does not, so
initially every page is prompt-only). A page whose prompt extraction or
generation fails simply has no picture; the pass continues. Status:
`done` if every page has an image, `partial` if some do, `failed` if none.
Two additions the home pipeline doesn't need: a fixed style directive
(child-appropriate storybook illustration, kept in one constant so it can be
tuned on-device) prepended to every prompt, and a drawing-phase time budget
(default 60 s) checked before each page so a slow Cloudflare can't hold The
End hostage; pages not reached have no picture and the status reflects it.

```swift
protocol ImageGenerating: Sendable {
    var supportsReference: Bool { get }
    func generate(prompt: String, reference: Data?) async throws -> Data?   // nil = declined
}
```

`CloudflareImageClient` posts `{"prompt": ..., "steps": 4}` to the endpoint
above with the bearer token and decodes the base64 JPEG from the response.
Any non-2xx status, `success: false`, or empty image throws a typed error
that the pass maps to "no picture for that page". The phone re-encodes
whatever comes back to at most 512 px on the long side, JPEG quality ≈ 0.8
(~50–100 KB), for both local display and upload. The exact JSON envelope
around the image (Cloudflare's v4 REST responses wrap results) is
confirmed against a real response in Phase 2's first task.

### `AppModel` and Settings changes

1. `connectAwayFromHome()` builds a `DemoStoryLibrary` (and an
   `IllustrationPass` only when both Cloudflare credentials are stored) and
   passes it to `DemoConnection`. It also sends
   `updateSettings(targetTurns:pageCount:)` after connecting, as `connect()`
   already does — today only the server path does.
2. One `LocalStoryStore` instance is shared by the demo path and the sync
   path (see Sync).
3. `setAwayFromHomeEnabled(_:)`, on an actual backend switch, also resets
   library state: `libraryStories`, `selectedStory`, cached page images,
   any pending story-detail fetch, **and the End-screen baseline**
   (`hasEstablishedLibraryBaseline`, `lastAcknowledgedConcludedStoryId`).
   Without the baseline reset, the first Library list after a switch would
   present a "newest story" different from the other backend's acknowledged
   id and hijack navigation to The End — the issue #36 pattern. A plain
   disconnect/reconnect within one backend deliberately does **not** reset
   the baseline, exactly as PR #42 left it.
4. Settings' hidden away-from-home card gains two secure fields, Cloudflare
   account ID and API token, stored in the Keychain (`KeychainStore` keys
   `cloudflareAccountId`, `cloudflareApiToken`) exactly like the Groq key.
   Illustrations are enabled only when both are present. This is Phase 2.

## Data flow

### Message handling

Every `ClientMessage` case gets an explicit demo-mode behavior:

| Message | Demo-mode behavior |
|---|---|
| `speechStart`, `speechEnd`, `interrupt` | Unchanged. (Mic audio arrives via the separate `send(audio:)`, also unchanged.) |
| `objectSeen`, `newStory` | Unchanged. |
| `updateSettings(turns, pages)` | Clamp to the server's bounds (turns 4–12, pages 3–10). Applies to the **next** story only: rebuild the arc if the current one hasn't started, otherwise leave it (never retroactive), exactly as `SessionRunner.handle_update_settings`. |
| `concludeStory(turnId)` | Cancel any in-flight turn (like a barge-in), set the turn id, run one turn with empty child text and `StoryArc.forceConcludeGuidance()`, mark the story done unconditionally, then follow the conclusion flow below. |
| `listStories` | `storyList` from the library, newest first. |
| `getStory(id)` | `storyDetail`, or an `error` frame (`no saved story with id '…'`) for an unknown id. |
| `synthesizePage(id, i)` | Invalid story/page → `error` frame and **no** `page_audio_done` (the client already handles that shape). Otherwise stream the on-device TTS chunks as `audio` events, then `pageAudioDone`. |
| `getPageImage(id, i)` | Invalid → `error` frame. Image present → one binary `audio` frame then `pageImageDone(hasImage: true)`. No image → `pageImageDone(hasImage: false)` alone. |
| `syncDemoStories` | Never sent to a `DemoConnection` (only the real-server connect path issues it). Handled as an explicit no-op with a comment saying exactly that, not folded into a shared catch-all. |

### A story concludes (natural or via "Finish this story")

Same order as the real server (`session.py`, the concluding-turn branch), so
the client's existing logic just works:

1. The reply audio streams, then `turnEnd`.
2. The transcript is saved locally as `pending` and queued for sync as
   today (`PendingDemoStore`). Arc and conversation reset for the **next**
   story using the current settings.
3. `rewritingStarted` is emitted — after the save, as on the server. With
   the concluding turn's playback finishing, this is what makes
   `readyToShowTheEnd` true and `AppModel` navigate to The End.
4. A background build runs, one at a time: `StorybookWriter` rewrite →
   local save (`done`, or `failed`) → Phase 2 illustration pass → statuses
   saved → `rewritingDone`. As on the server, `rewritingDone` comes after
   the **whole** pass, so "Read it now" un-greys when text and art are both
   ready.

## Sync

### Client

`AppModel.connect()` builds sync payloads from the local store plus any
legacy pending payloads. Each story keeps today's fields and gains an
optional `storybook` object, present only when the local rewrite finished
`done`:

```json
{"type":"sync_demo_stories","stories":[{
  "id":"a1b2c3d4","created_at":"2026-09-19T14:03:11Z",
  "turns":[{"speaker":"child","text":"…","interrupted":false}],
  "shared_facts":[["elephant","…"]],
  "storybook":{
    "title":"The Elephant Who Found a Kite",
    "pages":[{"text":"…","image":"<base64 JPEG, omitted if none>"}],
    "illustrations_status":"done"}}]}
```

The epilogue is deliberately not sent; the server derives it from
`shared_facts`. After the send succeeds, both stores are cleared for the
synced ids (`PendingDemoStore.clear()` as today, plus
`LocalStoryStore.remove`). The protocol change is backward compatible in
both directions: the server already accepts any story dict, so an old
server ignores the unknown `storybook` key and rewrites from the transcript;
an old phone sends none, so a new server behaves as today.

### Server

A new module, `server/tinytalk/synced_storybook.py`, validates and stores an
uploaded storybook; `SessionRunner.handle_sync_demo_stories` calls it after
`save_synced_story`. The server treats all client data as untrusted (see
`save_synced_story`, which discards the phone's id and forces
`rewrite_status: "pending"`), so it skips its own rewrite **only** when the
storybook passes every check below. Otherwise it leaves the story `pending`
and runs `_run_synced_rewrite`, today's behavior.

- Bounds: title 1–200 chars; 1–10 pages; each page text 1–2000 chars;
  each image ≤ 1.5 MB decoded.
- Images: must decode with PIL as JPEG or PNG and have a pixel area of at
  most 4.2 million (2048×2048), checked from the header before decoding to
  reject decompression bombs. (The phone's images are ≤ 512 px, so this is
  generous.) The server then **re-encodes** to PNG under a
  **server-generated filename** (`{story_id}-page-{i}.png`, the same shape
  the home pipeline uses, so `read_page_image` needs no change). Raw client
  bytes are never written to disk.
- Safety: `safety.find_blocked` runs over the title, every page, and the
  derived epilogue. Any hit rejects the whole storybook.
- Epilogue: recomputed from `shared_facts` with the server's existing
  formula; the uploaded text is ignored.
- Storage reuses `story_store.update_story_rewrite` (status `done`) and
  `update_story_illustrations` (`done` if every page has an image,
  `partial` if some do; not called if none). The synced path still does not
  touch `SessionRunner._machine` or send `rewriting_*` events.
- Logging: exactly one line per uploaded storybook, either "accepted"
  (page and image counts) or "rejected" with the reason. On-device
  verification relies on this to tell an accepted upload from a fallback
  rewrite.

## Error handling

Children never see a broken screen; every failure degrades to something the
existing UI already renders.

- **Rewrite fails after all attempts, or Groq is unreachable:** the story is
  marked `failed` and Library already renders "Couldn't finish this
  storybook". The transcript is kept, and syncs home transcript-only so the
  Mac can retry the rewrite.
- **One page's image fails, or the time budget runs out:** that page has no
  picture; `partial` or `failed` is recorded. Reading already renders
  picture-less pages.
- **No Cloudflare credentials:** text-only storybooks, silently.
- **Bad or expired token, or quota exhausted:** treated as an image
  failure, with one line in the debug log; nothing child-visible.
- **Groq free tier (30 requests/minute):** a story costs roughly 1–3
  rewrite calls plus one scene-prompt call per page, run sequentially, so
  it stays inside the limit.
- **Local disk write failure:** logged to the debug log; the story still
  syncs from the pending queue.
- **Unknown story or page id:** an `error` frame, which the client already
  treats as safe to clear.

## Testing approach

Following the project's existing conventions (fakes for protocol seams; no
real network in any suite):

- **Swift (`TinyTalkCoreTests`), with fakes:**
  - `SafetyTests`: `findBlocked` parity, mirroring `test_safety.py`.
  - `StorybookWriterTests`: mirroring `test_storybook.py` — prompt shape,
    tolerant parsing, retry on unparseable output, retry on an unsafe
    result, failure after the attempt budget, epilogue derived from facts
    and never model-written.
  - `LocalStoryStoreTests`: round trips, ordering, image files, removal.
  - `DemoStoryLibraryTests`: build flow, statuses, serialization of builds.
  - `DemoConnectionTests` (extended): event ordering
    (`turnEnd` → `rewritingStarted` → `rewritingDone`), and each message in
    the table above including the error-frame cases.
  - `IllustrationPassTests`: page 0 first, reference passing, per-page
    failure → `partial`, all fail → `failed`, time-budget cutoff.
  - `CloudflareImageClientTests`: request shape and response decoding
    through an HTTP seam.
  - `ProtocolTests`: sync payload encoding, with and without `storybook`.
- **Protocol-parity guard:** a test contains an exhaustive `switch` over
  `ClientMessage`, classifying every case as "produces a response" or
  "silent by design, with a stated reason". Adding a `ClientMessage` case
  fails to compile until it is classified, which is the mechanical answer to
  #24's "this keeps recurring" concern.
- **Python (`server/tests`):** `test_synced_storybook.py` — a valid upload
  stores `done` plus server-named PNGs; unsafe, oversized, malformed,
  wrong-format and bomb-sized uploads fall back to `pending`; a legacy
  payload with no `storybook` is unchanged; the epilogue is recomputed from
  facts; page counts are bounded. `test_session.py` — the
  `handle_sync_demo_stories` integration.

## On-device verification (the acceptance contract)

Per this repo's convention, the implementation plan restates these with the
exact worktree path, whether the server needs restarting, and whether the
iOS app needs rebuilding. Both phases need an iOS rebuild; the **server
change ships in Phase 1**, so the Mac server must be restarted from that
worktree before the sync steps.

**Phase 1** (Mac server stopped or its WiFi off; Groq key already saved):

1. Settings → turn on away from home; set turns to 4 and pages to 3. Create a
   story; it concludes after about 4 turns. Repeat and use "Finish this
   story" mid-story; it ends with a real closing line.
2. The End appears by itself after Elsie's last line finishes, showing a
   real title; "Read it now" enables within seconds.
3. Read it: 3 pages of prose. Tap 🔊 — the waiting ditty, then narration in
   the chosen voice; swipe pages and the audio stops.
4. Back out to Library: the story is listed with its title and 3 pages. Go
   Home → Read Stories works.
5. Turn away-from-home **off** (Mac on). Library must **not** show the demo
   story yet, and opening it must **not** jump to The End.
6. Connect to the home server. In the Mac server log, the story arrives as a
   validated upload (no rewrite is started). The home Library shows it
   `done` with the same title and pages.
7. Finish a story, then switch on airplane mode the moment Elsie's closing
   line ends. The rewrite can't reach Groq, so once The End settles Library
   shows "Couldn't finish this storybook". Turn airplane mode off and sync
   home: the Mac log shows a fallback rewrite from the transcript (not an
   accepted upload), and the story ends up `done` at home.

**Phase 2** (Cloudflare credentials saved in the hidden card):

1. Complete a story away from home: The End waits, then "Read it now"
   enables; every page has a picture.
2. Blip the network mid-pass (airplane mode for a few seconds): some pages
   have no picture, the story is still readable.
3. Sync home: the pictures appear in the home Library's Reading screen.
4. Clear the credentials: the next story is text-only with no error. Enter a
   wrong token: text-only, with a line in the debug log.

## Phasing

One spec, two plans, two PRs. Phase 1 is testable on-device with no new
accounts; Phase 2 depends on Phase 1's library and sync.

- **Phase 1 — local storybook.** `Safety.findBlocked`, `StorybookWriter`,
  `LocalStoryStore`, `DemoStoryLibrary`, the extended `DemoConnection`
  (settings, Finish-this-story, list/get, page audio, `rewriting_*` events,
  the protocol-parity guard), the `AppModel` wiring and mode-switch reset,
  and the sync change on both sides (the server validator handles images
  from the start, unit-tested with synthetic images, so the wire format is
  defined once).
- **Phase 2 — away illustrations.** `ImageGenerating`,
  `CloudflareImageClient` (its first task confirms the real response
  envelope), `IllustrationPass`, the Keychain/Settings fields,
  `get_page_image`, and uploading images with the sync payload.

## Open questions / risks

- **Character consistency.** FLUX.1 [schnell] takes no reference image, so a
  character may drift between pages. The initial mitigation is the fixed
  style directive plus asking the scene-prompt step to name the main
  character the same way on every page. Escalation ladder if that isn't good
  enough on-device: (1) derive a one-line character description once per
  story and prepend it to every prompt; (2) switch to a FLUX.2 multi-reference
  model with page 0 as the reference, mirroring the home pipeline.
- **Image safety.** The home pipeline relies on Stable Diffusion's safety
  checker; nothing equivalent runs on the phone path. Scene prompts derive
  from text that already passed the kid-safety check and carry a
  child-appropriate style directive; this is accepted for a
  parent-supervised, demo-only, optional path, and revisited if an
  inappropriate image is ever seen.
- **Privacy exception.** Story scene text goes to Cloudflare to produce
  images. This extends demo mode's existing, household-sanctioned exception
  to "free/local models only" (Groq already receives the whole
  conversation) — parent-gated, optional, and off unless credentials are
  entered.
