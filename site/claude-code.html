WORKING WITH CLAUDE CODE

AI made code cheap. My attention became the bottleneck.

When generating changes is nearly free, two things become scarce: the model's useful context, and my time to verify. Four habits built around that — two of them skills I wrote with Claude, /handoff and /fix-issues.

01 — CONTEXT/handoff

Stop a session before it stops working well

Long sessions degrade: settled decisions get re-debated, and automatic compaction keeps what's recent rather than what matters. So I start one session per substantial task, and at about 70% context I run my /handoff skill, /clear, and start fresh from the generated progress.md summary.

.claude/progress.md
WorktreeCurrent goalFiles touchedDecisions (and why) Known failing checksNext 3 actionsDo NOT redoRelated spec

Every section is required. Missing checks are written as “not run this session” — never implied to pass. Decisions and “do not redo” are the parts compaction loses first.

One note per worktree, not per repo

With several worktrees mid-task, “the progress note” is ambiguous. The skill resolves which checkout it's in and hands back an absolute path plus the exact directory to resume from — a session started one folder over would silently read the wrong note.

02 — PARALLELISMgit worktrees · /color · /rename

Several sessions, each in its own worktree

Each task gets its own checkout and branch, so sessions can't touch each other's files and nothing merges until it's ready. The bigger change is what gets worked on: with more than one slot, the small diagnostic or docs refresh no longer loses to the next feature.

/color + /rename

Four identical terminals is how you test the wrong branch for twenty minutes. A colour and a name turn “which one was the mic fix?” into recognition, not recall.

Check before trusting local state

A PR merged by one session once made another's branch look stale. New sessions now list open PRs and worktrees first.

Cap it at four

Five heavy agents at once hit a rate limit and four died. The cap is an observed limit, not a guess.

03 — SEQUENCEdesign → spec → implement

Settle the design before the coding session starts

Exploring layouts in code means every rejected idea becomes code to unwind. I explore visually first — in Claude's design tool or Google Stitch — then hand Claude Code a decision, not a conversation.

1 · DESIGN

Divergent and disposable

Many directions, real content, no code. Product questions get answered here.

2 · SPEC

Written, approved, dated

One per sub-project, with non-goals and rejected options — so no later session re-proposes them.

3 · IMPLEMENT

Task by task, then on-device

“Tests pass” isn't done. Every change ships with a numbered script for testing on the phone.

Privacy check In Google Stitch, turn off Allow AI Model Training when a project's material shouldn't be used for training.
04 — BATCHING/fix-issues

AI shortens the fixing. The scarce resource is human testing time.

Every fix here needs a person, a phone and real speech to verify. Fixing issues one at a time means a test session per fix and a context switch each time. So issues go into GitHub as a backlog, and get fixed in batches that I test once using my skill, /fix-issues.

Triage: only fix what needs no human decision

Fix
Cause and fix derivable from the issue and code; a test can verify it.
Diagnostics
Only reproducible on real hardware → add logging, change no behaviour.
Needs decision
Product or design choice → that's a conversation, not an agent.
Claimed
An open PR already addresses it, or touches the same files.
Can't verify
Needs credentials or hardware the agent can't reach.

Rules learned the hard way

Issues that touch the same code share one agent — parallel edits to one file become merge conflicts.

Re-run everything after merging. Clean textual merges were semantically broken twice.

Say “compiled only” when that's all it is. Never imply on-device verification that didn't happen.
